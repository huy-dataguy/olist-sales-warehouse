# Verification strategy and evidence gates

## Scope of current work

Design/specification and data-contract verification only, per the user's explicit choice. No Docker/database provisioning, application implementation or production-ready claim is part of this turn.

## Verification ladder

1. Static design: unique requirements, covered task graph, noncyclic dependencies, local links, schema validity and traceability.
2. Data/contract: real archive identity/schema, independently computed source baseline and golden fixture with manually authored expectations.
3. Semantic offline: pinned dbt syntax, time spine, conformed dimension graph, SQL generation and rejection of invalid groupings.
4. Integration: actual isolated PostgreSQL and S3; controlled migrations, roles, data load, dbt facts/dimensions.
5. Runtime semantic: real MetricFlow result execution with explicit release/source-cut identity and SQL parity.
6. Operational: Airflow scheduling/retry/failure, idempotency, late/corrected data, fencing and release isolation.
7. Consumer: three dashboards whose cards share one pinned release and metric semantics.
8. Recovery/security/capacity: timed isolated restore, rollback, permission denials, secret hygiene, resource/SQL measurements.
9. Handoff: all required checks/evidence complete, no skipped check counted as pass.

## Evidence dimensions

Record command, environment/locks, artifact/source hashes, source_cut, release_id, contract/model/semantic versions, start/end times, exit status, expected result and actual result. Store machine-readable summaries plus concise logs. A negative scenario is a pass only if the intended failure and its invariants are observed.

Current source profiling and offline compilation are real evidence for their bounded scope; they do not certify Warehouse/Airflow/Metabase startup or production behavior.

## Golden data independence

Fixtures and expected JSON are authored separately. The verifier computes results from input and compares to those expectations. Production code will be tested against the same fixture; expected values must not be generated by the transformation under test.

Fixture intentionally covers:
- two item rows and two payment rows on one order,
- same durable customer across multiple source IDs, dates and states,
- canceled and unavailable orders,
- missing children and category,
- delivered status with absent delivery timestamp,
- payment discrepancy at cent-level tolerance,
- valid/late Type 2 changes, repeated payload, exact-boundary lookup,
- inferred dimension member receiving attributes without a key change.

Names/IDs in fixtures are synthetic and marked accordingly. They never become evidence of Olist business history.

## Kimball gates

Check bus coverage, grain uniqueness, applicable nonnull dimension keys, stable integer SK registry, role-playing dates, no fact-to-fact aggregation, unknown/inferred member policy, referential integrity inside the same release, measure additivity, ratios/distincts at requested grain, SCD2 no overlap/current uniqueness and late-arrival restatement.

## Release isolation matrix

Test old release remains visible while new work builds, candidate snapshot incomplete, export partially written, parity failure, stale lease owner, concurrent promoter, valid publish commit with lost acknowledgement, and BI link update failure after commit.

Validate each presentation join uses a common release; metric requests require their explicit semantic release; all cards use a pinned release parameter. A browser refresh during promotion must not silently mix versions.

## Replay and performance

For the same accepted artifact/revision set compare incremental output with a rebuilt target: logical natural-key sets, money/counts, DQ issues and semantic outputs. With the retained/restored registry, SK mappings must remain identical. A fresh independent registry can allocate different integers: normalize to natural/effective identities for equivalence instead of declaring a false failure. Logical hashes exclude run/release/capture/audit identifiers; validate that metadata independently. Include an old order whose status changes and whose full child set must be recomputed.

Benchmark real queries on identical accepted inputs/results. Record plan, row estimates/actuals, buffers, indexes, repetitions and cache conditions. No speedup is assumed. Optional stress data is labeled separately from real-source counts.

## CI implementation contract

Planned .github/workflows/ci.yml: static/spec/contracts/fixtures and offline semantic probe.
Planned integration workflow/profile: fresh disposable services, actual storage/data/dbt/semantic tests and archived evidence.
Planned release workflow: reviewed migration + restore/capacity/consumer checks.

The current executable design checks remain scripts/profile_source.py, scripts/probe_semantics.py, scripts/validate_design.py and the new design-contract verifier. All service-dependent make targets remain planned.
